# Photo Wall archive and retention

Retention starts with the first upload signed by the updated Photo Wall upload function. The function adds the `party_media_retention_v1` tag to new authenticated uploads. Every 15 minutes the worker scans this tag and writes to `photo_retention_new_jobs`. This also covers uploads that never reached the live queue or were later removed from it. Existing Cloudinary assets, archive masters, and legacy job records are outside this workflow.

The worker downloads the original Cloudinary upload and writes it to the private Drive master folder. Firestore stores a server-only job per Cloudinary asset and version. Before accepting a copy, the worker checks its parent folder, size, SHA-256, asset and version metadata, trash state, and sharing permissions. A failed request is retried. Drive file IDs are reserved before upload so a retry after an ambiguous response reuses the same file. The worker never deletes Drive masters.

After four days, cleanup rechecks the Cloudinary asset and its bytes, rechecks the private Drive copy, and requests Cloudinary deletion by asset ID with CDN invalidation. The four days start at the later of the Cloudinary creation time and the current version time. Cloudinary CDN invalidation can take time to propagate. A failed backup or recheck keeps the source in Cloudinary.

## Deploy and validate

1. Deploy the new-upload version of `createPhotoWallUpload` and `retainPhotoWallMedia` to `dj-photo-wall` with deletion disabled. Resume the Cloud Scheduler job after the new worker is active. Verify a private test upload, then deploy the Firestore rules and publish the Photo Wall pages.
2. Set `PHOTO_DRIVE_ARCHIVE_FOLDER` to the private archive folder ID in the Functions environment. Grant the Functions runtime identity `Secret Manager Secret Accessor` on each of the three specific secrets. Use the existing Secret Manager versions for `cloudinary-api-key`, `cloudinary-api-secret`, and `google-drive-token`. The Drive secret must contain an OAuth refresh credential with `refresh_token`, `client_id`, and `client_secret`. A scoped credential needs write access to the existing archive folder. If a `drive.file` credential cannot see the folder, explicitly authorize that folder for the same OAuth app, then add an updated version securely in Secret Manager.
3. Run `firebase-schedule-retainPhotoWallMedia-us-central1` from Cloud Scheduler. Check logs and `photo_retention_new_jobs` for a `verified` record. Confirm its matching original opens from the configured Drive folder and has no public sharing. Test a photo and a video on the projector and with a fresh guest code.
4. Set `PHOTO_RETENTION_DELETE_ENABLED=true` in the Functions environment and redeploy only `retainPhotoWallMedia` after successful live backup verification. Eligible jobs are revisited automatically. Remove the setting and redeploy the worker to suspend cleanup while backups continue.

New uploads use Cloudinary authenticated delivery. The guest gallery issues time-limited preview and download links that expire at the guest pass deadline. When an event closes, the gallery closes and the server stops issuing links. Previously issued links reach their original expiry. Pre-existing public uploads are excluded from the new guest gallery and keep their existing Cloudinary delivery. Admin and projector sessions can still view them. The public reaction screen shows the uploader's name without a private media thumbnail.

A Drive master contains the original **uploaded to Cloudinary**. The guest upload page can crop and resize photos before that upload. Media without the new retention tag, and files larger than 100 MiB, require separate archive handling. Oversize tagged jobs log a failure and keep their Cloudinary source.
